## Критические / High

### H-1. `apply_edit` panic на инвертированном LSP-диапазоне
**Severity:** high
**Location:** `server/crates/php-lsp-parser/src/parser.rs:65-67`

`apply_edit` не проверяет `start_byte <= old_end_byte`. `rope.remove(start_char_idx..end_char_idx)` (строка 67) вызывает panic, если LSP-клиент пришлёт диапазон где `end < start` (collapsed/reversed range).

```rust
let start_char_idx = self.rope.byte_to_char(start_byte);
let end_char_idx = self.rope.byte_to_char(old_end_byte);
self.rope.remove(start_char_idx..end_char_idx);  // panic если start > end
```

**Fix:** Перед мутацией: `let old_end_byte = old_end_byte.max(start_byte);`

> **Комментарий Codex — подтверждено, но medium:** инвертированный диапазон действительно приводит к `rope.remove(start..end)` с `start > end`. Предложенный fix неполон: нужно валидировать или нормализовать весь диапазон и согласованно менять `old_end_byte` и `old_end_point`, а не только одно byte-значение.

**Как буду исправлять:**

1. До любых преобразований и мутаций проверю LSP-позиции лексикографически: `(end_line, end_char) < (start_line, start_char)` считается ошибкой. Равенство позиций оставлю валидным — `start == end` означает обычную вставку и не вызывает panic.
2. Изменю `FileParser::apply_edit` так, чтобы он возвращал `Result<(), ApplyEditError>`. Parser-level guard останется последней защитой: при reversed range функция вернёт ошибку до изменения rope и tree-sitter tree.
3. В `didChange` добавлю preflight всех `contentChanges` до применения первого edit. Если хотя бы один range reversed, будет отклонена вся notification: parser, tree, document version и workspace index сохранят предыдущий согласованный snapshot. Для notification нет JSON-RPC response, поэтому сервер запишет warning с URI, version и диапазоном и дождётся следующего валидного full-text change или reopen.
4. Для валидного edit сохраню текущий порядок вычислений, но добавлю проверяемый инвариант `start_byte <= old_end_byte` перед `rope.remove`. В `InputEdit` будут передаваться позиции, вычисленные из того же принятого диапазона.

Простой `old_end_byte.max(start_byte)` использовать не буду: при reversed range он меняет byte offset, но оставляет `old_end_point` от исходной позиции. Такой `InputEdit` внутренне противоречив и может рассинхронизировать rope и tree-sitter.

**Regression-тесты:**

- collapsed range (`start == end`) вставляет текст;
- reversed range в одной строке возвращает ошибку без panic и без изменения source/tree;
- reversed range между строками также не меняет состояние;
- reversed UTF-16 range рядом с emoji не повреждает multibyte текст;
- LSP e2e: невалидный `didChange` не завершает сервер, не публикует частичный index snapshot, а следующий валидный full-text change восстанавливает синхронизацию.

**Статус реализации Codex (2026-08-14): исправлено.** Добавлена parser-level ошибка до мутации, атомарный preflight notification и generation-aware ожидание full-text resync. Состояние resync сохраняется при rename открытого файла и очищается при успешной полной синхронизации, reopen, close или delete. Regression-тест также проверяет, что incremental change после reversed range и rename остаётся заблокированным, а full-text change восстанавливает parser и workspace index.

### H-2. `source_byte_offset` может panic на multibyte границе
**Severity:** high
**Location:** `server/crates/php-lsp-parser/src/semantic.rs:1714-1723` (используется в `:709-713`)

`source_byte_offset` складывает byte column с byte offset строки. `NamespaceScope.range` — байтовые колонки (см. `php-lsp-types/src/lib.rs:458-463`), так что для ASCII это корректно. Но `&source[scope_start.min(source.len())..scope_end.min(source.len())]` (строка 713) slice'ит `&str` по offset, который может оказаться внутри multibyte символа (если column попадает в середину emoji/CJK) → **panic "byte index is not a char boundary"**.

**Fix:** Конвертировать byte column → byte offset с учётом char boundaries (через существующие utf16-хелперы или `source.char_indices()`), либо clamp к ближайшей char boundary.

> **Комментарий Codex — отклонено:** `NamespaceScope.range` строится из `tree_sitter::Point` (`node_range`, `start_position`, `end_position`). Эти позиции имеют byte columns, но всегда указывают на границы UTF-8 символов. `source_byte_offset` восстанавливает исходный byte offset, поэтому показанный slice не попадает внутрь emoji/CJK.

### H-4. `get_direct_members` — O(N²) под DashMap read guard
**Severity:** high (scalability)
**Location:** `server/crates/php-lsp-index/src/workspace.rs:477-491`

`get_direct_members` итерирует **все** файлы и **все** символы, удерживая DashMap read guard (`self.file_symbols.iter()`) на протяжении полного скана. Вызывается из `resolve_member_in_hierarchy` на **каждый** member resolution и рекурсивно для каждого parent/trait. Квадратичная сложность по workspace + lock contention.

**Fix:** Построить inverted index `parent_fqn -> Vec<member>` (обновлять в `update_file_with_references`/`remove_file`), освобождать guard перед возвратом клонов.

> **Комментарий Codex — подтверждено, но medium/performance:** каждый direct-member lookup сканирует все `file_symbols`, а обход иерархии повторяет скан для каждого типа. Это реальный hotspot и lock-contention risk, но стоимость одного lookup ближе к `O(workspace_symbols × hierarchy_depth)`, а не автоматически `O(N²)`. High требует профиля на большом workspace.

**Как буду исправлять:**

1. Добавлю в `WorkspaceIndex` производный inverted index с ключом `case_insensitive_fqn_key(parent_fqn)`. Значение будет immutable/COW bucket, сгруппированный по исходному файлу: URI, общий immutable `Arc<FileSymbols>` snapshot и индексы нужных элементов в `FileSymbols.symbols`.
2. Не буду постоянно хранить вторую полную копию каждого `SymbolInfo`: bucket содержит только компактные locators. Это важнее простого `DashMap<String, Vec<Arc<SymbolInfo>>>` для больших stub/workspace-индексов, где дублирование сигнатур и PHPDoc заметно увеличило бы память.
3. В `update_file_with_references` сериализую полную замену snapshot для одного URI, удалю только устаревшие contributions и атомарно заменю COW buckets для сохранившихся parent FQN. Индексировать буду все символы с `parent_fqn`, а не захардкоженный список kinds, чтобы сохранить текущее поведение для методов, свойств, class constants, enum cases и virtual members.
4. В `remove_file` удалю contributions только данного URI из затронутых parent buckets и удалю опустевшие buckets. Символы того же parent FQN из другого файла должны сохраниться — это нужно для корректной обработки дубликатов и последовательной замены файлов.
5. `get_direct_members` будет делать один lookup по нормализованному parent FQN, клонировать `Arc` bucket и сразу отпускать его DashMap guard. Затем он прочитает только перечисленные immutable file snapshots: старый bucket продолжает владеть старым согласованным `Arc<FileSymbols>`, поэтому reader не блокируется writer'ом и не может смешать версии файла.
6. Формат disk cache менять не потребуется: inverted index является производным и автоматически восстанавливается существующими вызовами `update_file_with_references` при загрузке cache. Полный hierarchy-result кэшировать не буду, потому что template substitutions и invalidation всех descendants сделали бы его существенно сложнее и рискованнее.

Ожидаемая стоимость direct lookup станет `O(1 + K)`, где `K` — число прямых членов конкретного parent, а обход иерархии — `O(суммы членов посещённых типов)`, без скана всех workspace symbols на каждом шаге. Глобальный `file_symbols.iter()` и удержание его guards из этого hot path исчезнут.

**Regression-тесты:**

- direct lookup не зависит от регистра parent FQN и сохраняет PHP-правила сопоставления имён членов;
- trait, mixin, parent class и interface по-прежнему обходятся в прежнем порядке с template substitutions;
- повторный `update_file_with_references` удаляет старые members и публикует новые;
- `remove_file` очищает только contributions удалённого URI и сохраняет одноимённый parent из другого файла;
- загрузка index cache восстанавливает direct-member index;
- concurrent lookup во время замены файла возвращает согласованный старый или новый snapshot, но не смешивает поколения;
- структурная проверка подтверждает, что lookup не итерирует `file_symbols`; при необходимости добавлю отдельный benchmark на synthetic workspace без нестабильных wall-clock assertions в unit-тестах.

> **Комментарий Codex — исправлено 2026-08-14:** workspace-wide scan удалён из `get_direct_members`; lookup теперь читает COW bucket по нормализованному parent FQN и только указанные в нём элементы общего immutable `Arc<FileSymbols>` snapshot. Полная замена и удаление одного URI сериализованы, поэтому два writer'а не могут переопубликовать устаревший bucket, а reader во время обновления видит целый старый либо новый snapshot без пустого окна. Disk cache восстанавливает производный индекс через обычный update lifecycle. Добавлены regressions для замены файла, duplicate parent/remove, cache roundtrip и детерминированной конкуренции двух writer'ов с reader'ом; focused tests, fmt, Clippy и `git diff --check` прошли с `CARGO_BUILD_JOBS=1`, повторная проверка Verifier — GO.

### M-1. `phpdoc.rs` underflow panic: `idx - 4` / `idx - 3` / `idx - 1`
**Severity:** medium
**Location:** `server/crates/php-lsp-parser/src/phpdoc.rs:708-716`

`find_phpdoc_variable_token` делает `idx - 4` (для `&...`), `idx - 3` (для `...`), `idx - 1` (для `&`) без проверки, что `idx` достаточно велик. На malformed PHPDoc где `$` близко к началу `rest` → underflow `usize` → panic "byte index out of bounds".

```rust
let name_start = if prefix.ends_with("&...") {
    idx - 4  // panic если idx < 4
} else if prefix.ends_with("...") {
    idx - 3
} ...
```

**Fix:** `idx.saturating_sub(4)` + проверка, или `prefix.len().checked_sub(...)`.

> **Комментарий Codex — отклонено:** underflow невозможен: `prefix.ends_with("&...")` уже доказывает `idx == prefix.len() >= 4`; аналогично для `"..."` и `'&'`. ASCII-суффиксы также гарантируют корректные byte offsets.

### M-2. `is_null_coalesce_probe` — raw text search `??` без учёта строк/комментариев
**Severity:** medium
**Location:** `server/crates/php-lsp-parser/src/semantic.rs:1284-1288`

`text.find("??")` ищет `??` в сыром тексте parent-ноды, включая строковые литералы и комментарии. Переменная внутри выражения с `??` в строке (напр. `$x = "a??b"; $y;`) ложно классифицируется как null-coalesce probe → подавляется `UndefinedVariable` диагностика.

**Fix:** Искитать `??` только как `coalesce_expression` tree-sitter ноду (обход children), а не raw text.

> **Комментарий Codex — подтверждено, medium:** raw search по предку действительно может принять `??` внутри строки или комментария за оператор. Однако пример выше с двумя отдельными statements не воспроизводит подавление: fake `??` расположен до `$y`, а текущий код возвращает `node_offset < operator_offset`. Надёжный repro — `consume($missing, "a??b");` или `consume($missing /* ?? */);`, где переменная идёт раньше fake-оператора в общем ancestor. Кроме того, в используемом `tree-sitter-php 0.23.11` отдельного `coalesce_expression` нет: настоящий `??` — это `binary_expression` с полем `operator`, чей `kind()` равен `"??"`.

**Как буду исправлять:**

1. Уберу `source` из `is_null_coalesce_probe`: для классификации больше не потребуется читать сырой текст или вычислять byte offset оператора.
2. При подъёме от `variable_name` по ancestors буду хранить непосредственную ветку, через которую пришёл к очередному parent. Реальным coalesce буду считать только `parent.kind() == "binary_expression"` с `parent.child_by_field_name("operator").kind() == "??"`.
3. Для ближайшего реального coalesce верну `true` только если сохранённая ветка совпадает с `left` field. Если переменная находится в `right`, сразу верну `false` и не позволю внешнему `??` ошибочно скрыть обычное чтение правого операнда. Границы function/method/closure/program останутся прежними.
4. Отдельно сохраню isset-style probe для левой ветки `augmented_assignment_expression` с точным operator `??=`: прежний raw search неявно обеспечивал это поведение. Остальные augmented assignments не будут затронуты. Строки, interpolated text и комментарии автоматически исключаются, потому что их `??` не является operator field AST-узла.
5. Добавлю regressions в плоский `semantic_tests.rs`: настоящий левый operand и array access не дают `UndefinedVariable`; правый operand даёт; `??` после переменной внутри строки и комментария не подавляет ошибку; chained/nested coalesce соблюдает ближайший left/right operand; LHS `??=` остаётся безопасным probe.

После изменения запущу focused semantic tests, все parser tests, parser Clippy с `-D warnings`, `cargo fmt --all --check`, `git diff --check` и обязательный Verifier. Полный workspace run для parser-only изменения не нужен; все команды будут с `CARGO_BUILD_JOBS=1`.

> **Комментарий Codex — исправлено 2026-08-14:** `is_null_coalesce_probe` больше не читает raw source. Он распознаёт ближайший `binary_expression` с operator `??` либо `augmented_assignment_expression` с operator `??=` и подавляет `UndefinedVariable` только для его левой AST-ветки; правая ветка остаётся обычным чтением. Добавлены regressions для direct/array/chained/nested operands, строк и комментариев с fake `??`, а также LHS `??=`. Все 286 parser tests, parser Clippy с `-D warnings`, fmt и `git diff --check` прошли с `CARGO_BUILD_JOBS=1`; Verifier — GO.

### M-3. `byte_offset_to_point` off-by-one на CRLF
**Severity:** medium
**Location:** `server/crates/php-lsp-parser/src/symbols.rs:1240-1253`

`byte_offset_to_point` считает `\r` в колонку (`offset - line_start` включает `\r` перед `\n`). Для атрибутов/диапазонов в конце строки на CRLF-файлах колонка off-by-one. Используется для `SymbolAttribute.range`.

**Fix:** Учитывать `\r\n` как один перенос строки, или убирать `\r` из column (через `source.split('\n')` как `Utf16LineIndex`).

> **Комментарий Codex — отклонено:** функция вычисляет tree-sitter byte column как расстояние от байта после последнего `\n`. Для CRLF это корректно: `\r` остаётся байтом предыдущей строки. `SymbolAttribute.range` документирован как byte-backed, поэтому UTF-16/LSP semantics здесь не требуются.

### M-4. Cross-scope leak параметров в completion
**Severity:** medium
**Location:** `server/crates/php-lsp-completion/src/provider.rs:590-610`

`provide_variable_completions` итерирует **все** символы в `file_symbols.symbols` и собирает параметры **всех** функций/методов как completable variables, без фильтрации по scope (enclosing function). При вводе `$` внутри `functionA` предлагаются параметры из `functionB`, `functionC`.

**Fix:** Фильтровать символы по `range` содержит курсор (передать cursor range в `provide_variable_completions`, как `provide_completions_at_range`).

> **Комментарий Codex — подтверждено, medium:** production вызывает range-aware provider, но `provide_variable_completions` всё равно добавляет параметры всех функций файла. Следующий scoped helper только добавляет локальные переменные и не удаляет чужие параметры. Нужен cursor/enclosing-callable filter и regression с двумя функциями.

**Как буду исправлять:**

1. Передам `cursor_range` из `provide_completions_at_range` через общий dispatcher до ветки `CompletionContext::Variable`; внутренний параметр будет `Option<(u32, u32, u32, u32)>`, чтобы остальные completion contexts не дублировали код.
2. Добавлю `current_callable_symbol_at_range`: он рассмотрит только `PhpSymbolKind::Function | PhpSymbolKind::Method`, оставит символы, чей полный byte-backed `SymbolInfo.range` содержит cursor point, и выберет самый вложенный range. Class/interface symbols и PHPDoc virtual methods не должны становиться источником параметров вне собственного callable body.
3. `provide_variable_completions` перестанет сканировать signatures всего `file_symbols.symbols`: параметры будут браться только из signature выбранного callable. Prefix filtering, type detail, sorting и deduplication сохранятся; promoted constructor parameters попадут через signature текущего constructor method без отдельного списка или hardcode.
4. Для публичного legacy `provide_completions`, у которого нет cursor range, выберу консервативное поведение: не добавлять параметры named callables вообще. Угадать scope по первому/единственному символу небезопасно. Production уже использует `provide_completions_at_range`; существующий range-less unit-тест variable completion будет переведён на range-aware API.
5. AST-список `local_variable_names_at_position` станет финальным authority для production variable items: перед merge server удалит provider-параметры, которых нет в точном AST scope, сохранив typed detail у разрешённых items. Сам parser helper перестанет обходить nested callables, добавит explicit anonymous-function `use` captures и outer declarations для arrow-function auto-capture; это закрывает случай, когда cursor находится внутри closure, отсутствующей в `FileSymbols.symbols`.
6. Добавлю unit regressions для двух функций и двух методов, global cursor, вложенного named callable, prefix/type detail, constructor promoted param, nested-scope traversal, closure captures и arrow captures. Добавлю completion E2E с двумя callables и anonymous closure, чтобы доказать, что production wiring не возвращает параметры соседнего/невидимого scope и при этом сохраняет локальные/closure параметры.

После изменения запущу все parser/completion crate tests, focused `e2e_completion`, parser/completion/server Clippy с `-D warnings`, `cargo fmt --all --check`, `git diff --check` и обязательный Verifier с `CARGO_BUILD_JOBS=1`.

> **Комментарий Codex — исправлено и усилено 2026-08-17:** provider больше не сканирует signatures всего файла: range-aware path выбирает самый вложенный `Function`/`Method` по half-open range, а range-less API не угадывает callable. В production точный AST scope является финальным фильтром variable items; parser helper не заходит в nested callables, поддерживает simple/variadic/promoted parameters, explicit closure `use`, arrow auto-capture и корректную видимость `$this` через instance/static methods и closures. **Severity:** medium
**Location:** `server/crates/php-lsp-server/src/lsp/diagnostics.rs:53-54`

5. Одинаково переведу PHPStan и Psalm. `psalm_issue_path_matches` будет использовать тот же matcher, поэтому target canonicalize также выполнится один раз для всего массива issues.
6. Дополнительно заменю прямые `file_path.exists()` в async PHPStan/Psalm handlers на `tokio::fs::metadata(...).await`: иначе после исправления parser path в тех же analyzer handlers останется другой синхронный stat на runtime thread.

### M-10. TS: нет SIGKILL-эскалации на зависшем сервер-процессе
**Severity:** medium
**Location:** `client/src/extension.ts:530-551`

`terminateManagedServerProcess` вызывает `kill()` (SIGTERM) + ждёт 1с. Если сервер игнорирует SIGTERM (deadlock, tight loop), таймер срабатывает, функция resolve'ится, но orphaned child продолжает работать. Нет SIGKILL-эскалации и логирования still-alive PID.

**Fix:** После 1с grace, если процесс жив — `kill("SIGKILL")` + залогировать PID.

> **Комментарий Codex — подтверждено, medium:** после 1 секунды функция завершается, даже если child всё ещё работает. Нужны повторная проверка `childProcessIsRunning`, поддерживаемая платформой hard-kill эскалация, ожидание exit и явный log результата.

**Как буду исправлять:**

1. Вынесу generic process-termination state machine из `extension.ts` в отдельный TS-модуль без зависимости от VS Code, принимающий `ChildProcess`, reason, logger и configurable grace/force-wait durations. Extension оставит только получение приватного `_serverProcess` и передачу `lifecycleLog`.
2. Разделю понятия «signal был отправлен» и «process завершился». `ChildProcess.killed` не буду использовать как liveness: Node выставляет его сразу после `kill()`. Живым считаю handle с PID и одновременно `exitCode === null && signalCode === null`; это также позволит fallback увидеть процесс, которому language client уже послал signal, но который не вышел.
3. Добавлю `waitForChildExit`: он подпишется на `exit`, поставит bounded timer, повторно проверит exit state после установки listener для закрытия race и при любом исходе снимет listener/таймер. Функция вернёт `true` только при наблюдённом завершении.
4. Первая фаза явно отправит `SIGTERM`, проверит boolean результата `child.kill("SIGTERM")`, залогирует PID/signal и подождёт grace interval. Throw/`false` не завершат fallback молча: если handle всё ещё жив, state machine сразу перейдёт к hard kill.
5. После grace повторно проверю `exitCode/signalCode` и исходный PID. Если процесс жив, залогирую эскалацию и вызову `child.kill("SIGKILL")`. Для direct executable, используемого `ServerOptions`, Node поддерживает этот signal и на Unix, и на Windows; shell/process group здесь не создаются, поэтому `taskkill`/shell command не нужен.
6. После SIGKILL будет второй bounded wait. Итоговый log различит graceful exit, forced exit, signal-send failure и всё ещё живой PID с `exitCode`, `signalCode` и `killed`. Helper вернёт typed result, чтобы `stopLanguageClient` не называл процесс успешно остановленным при финальном `still-running`.
7. Добавлю testable fake-child regressions: unavailable/already-exited handle; synchronous и delayed exit на SIGTERM; `killed=true`, но process жив и требует SIGKILL; exit после SIGKILL; ignore/throw/false для обоих signals; final still-alive logging; listener/timer cleanup и race exit между signal/listener registration.
8. Добавлю отдельный `client/scripts/check-server-process.mjs`, который bundle'ит новый модуль через esbuild и запускает state-machine tests с короткими injected timeouts. Включу его в `npm run lint`, затем запущу client lint и production build.

После изменения выполню новый process check, полный `npm run lint`, `npm run build`, `git diff --check` и обязательный Verifier.

> **Комментарий Codex — исправлено 2026-08-17:** termination вынесен в независимый state-machine module. Liveness определяется по PID/`exitCode`/`signalCode`, а не по немедленно выставляемому `killed`; после bounded SIGTERM grace выполняются явный log, SIGKILL и второй bounded wait. Listener/timer очищаются при exit/timeout/race, signal false/throw не обрывает эскалацию, PID change блокирует hard kill, а финальный typed result не позволяет lifecycle сообщить ложный successful stop при живом процессе. Новый fake-child check покрывает graceful/forced/still-running, обе signal failure modes и listener race и включён в client lint. `check:server-process`, полный `npm run lint`, production `npm run build` и `git diff --check` прошли; Verifier — GO.

### L-3. Range-formatter wrapper может инжектить `<?php`
**Severity:** low
**Location:** `server/crates/php-lsp-server/src/lsp/formatting.rs:212-222`

4. Исправлю два существующих positive range-formatting E2E: их fake formatter сейчас возвращает только fragment и тем самым сам нарушает wrapper contract; он будет возвращать `<?php` + formatted fragment, а ожидаемый edit останется без synthetic tag.
